# 项目经验总结

本文档用于记录在本项目（移动端商品展示与筛选页面）开发和部署过程中积累的宝贵经验与踩坑记录，方便后续查阅和复用。

## 1. Vite 构建工具下的静态资源处理机制

在将项目部署到服务器后，曾遇到过“本地运行正常，但服务器上图片裂开（404）”的问题。这主要是由于对 Vite 的静态资源打包机制理解不深导致的。

### 踩坑现象
在 `mockData.ts` 中直接硬编码了图片的绝对路径：
```javascript
// 错误示范：本地能跑，打包后会丢失
imageUrl: '/src/assets/iphone-14.jpg'
```

### 原因分析
在 Vite（以及 Webpack 等现代构建工具）中，`src` 目录下的所有文件都被视为**模块（Module）**。
- **本地开发**：Vite 的开发服务器能直接顺着字符串路径读取电脑硬盘上的文件。
- **打包构建**：打包器（Rollup）在扫描代码时，如果没有发现通过 `import` 或 `require` 明确引入这张图片，它会认为该图片是“未被使用的冗余文件”，从而**不会**将其打包进最终的 `dist` 目录中。
- **结果**：服务器上根本没有这些图片文件，导致访问 404。

### 解决方案与最佳实践

在现代前端项目中处理图片/静态资源，应严格遵循以下分类存放原则：

#### 场景一：需要被构建工具处理的资源（放 `src/assets`）
- **适用对象**：小图标、组件专用的背景图、Logo 等。
- **处理方式**：必须通过 `import` 显式引入。打包器会对它们进行压缩、重命名（打上 Hash 值以防缓存），并自动放入打包目录。
```javascript
import logoImg from '../assets/logo.png';
<img src={logoImg} />
```

#### 场景二：不需要被处理的大量动态资源（放 `public` 目录）
- **适用对象**：像本项目中几百条 Mock 数据依赖的商品图片、`favicon.ico`、或者外部引入的第三方庞大 JS 库。
- **处理机制**：放在 `public` 目录下的文件，Vite 在打包时会**原封不动地直接复制**到 `dist` 的根目录下，不进行任何编译或重命名。
- **使用方式**：在代码中**永远不要**写 `/public/` 前缀，直接使用根路径 `/` 即可。
```javascript
// 正确示范：将图片放入 public/assets/ 目录下
// 无论本地还是生产环境，都能正确映射到根目录的 assets 文件夹
imageUrl: '/assets/iphone-14.jpg'
```
